iOS audio probe

Start with CTL on a fresh reload, then E. Run one test at a time. Where a test says to lock the screen, lock it, count to twenty, unlock, then read the log. Judge sound by ear — the log cannot hear.

A · does el.volume work?

Plays a plain <audio>, ramps the volume down to 0.15 over 3s and back up over 3s. Listen.

B · does the graph survive a screen lock?

Plays through createMediaElementSource → gain → destination. Start it, lock the screen, count to twenty, unlock.

C · can it hand off to a plain element on the way into the lock?

Same graph, but on hidden it starts a second bare element at the same position and pauses the graph one; on visible it hands back. Start it, lock, count to twenty, unlock. Listen for a gap at each handover.

CTL · control: does a bare element dip at the lock anyway?

No graph, no handoff, one plain <audio> — the player you have today. Reload the page first, then start it, lock, count to twenty, unlock. If this dips too, the dip is iOS and the handoff is not to blame.

E · handoff without the gap

Same as C, but the second element plays alongside the whole time, muted and kept in step, so the handover is a mute toggle instead of a seek and a cold start. Start it, lock, count to twenty, unlock. Compare with C.

D · does resume() bring a dead graph back?

Only needed if the log says D APPLIES after you unlock. If the music came back by itself there is nothing to resume — that is the answer.
